# ВышКат — учёт парка кикшеринга

Консольное приложение на C# / .NET 10 для учёта транспорта и имущества сервиса «ВышКат». Проект использует интерфейсы предметных ролей, принципы SOLID и внедрение зависимостей через `Microsoft.Extensions.DependencyInjection`.

## Используемые технологии

- **Язык и платформа:** C#, .NET 10.
- **DI-контейнер:** `Microsoft.Extensions.DependencyInjection`.
- **Тестирование:** xUnit, NSubstitute.
- **Проверка покрытия:** `coverlet.collector`, отчёт Cobertura XML.

## Возможности приложения

Программа поддерживает добавление транспорта и вещей, просмотр парка и формирование отчётов.

**Транспорт:** `Bicycle`, `ElectricBicycle`, `ElectricScooter`.

**Вещи:** `Helmet`, `DockStation`, `ChargingCabinet`.

Основные правила:

- Транспорт проходит техосмотр, вещи принимаются без него. `ConditionScore` ниже 50 означает отказ, 50 и выше — допуск.
- Отклонённый транспорт не добавляется в `Fleet` и не занимает инвентарный номер.
- Номера генерируются с префиксами `BI`, `EB`, `SC`, `HE`, `DS`, `CC`. Повторы запрещены без учёта регистра и внешних пробелов.
- Для новичков подходят объекты с `EaseOfUse >= 6`. Для `ElectricScooter` дополнительно требуется `MaxSpeedKmh <= 25`.
- Суточное энергопотребление суммируется только у объектов, реализующих `IEnergyConsumer`.

Отчёты содержат общее количество имущества, количество объектов каждого типа, энергопотребление, список устройств для новичков и полный перечень имущества с названием и инвентарным номером.

## Архитектура и SOLID

**ISP — принцип разделения интерфейсов.** Наиболее явно выраженный принцип проекта. Каждый интерфейс описывает отдельную роль. Например, `Helmet` реализует `IInventoryItem`, а `DockStation` и `ChargingCabinet` дополнительно реализуют `IEnergyConsumer`. Вещам не требуются интерфейсы техосмотра и пригодности для новичков.

**SRP — принцип единственной ответственности.** `Fleet` отвечает за приём и хранение, `ServiceCenter` — за техосмотр, `InventoryNumberGenerator` — за номера, `FleetReportService` — за отчёты, `Demo` — за консольное взаимодействие. Приём и хранение объединены в `Fleet`, поскольку это позволяет сохранять инвариант: транспорт без успешного техосмотра не попадает в парк.

**DIP — принцип инверсии зависимостей.** `Fleet` зависит от `IServiceCenter`, а не от конкретного `ServiceCenter`. Реализация регистрируется в `Program.cs` и может быть заменена в тестах.

**OCP — принцип открытости/закрытости.** Отчёты учитывают объекты через интерфейсы. Например, новый объект с `IEnergyConsumer` автоматически участвует в расчёте энергопотребления.

**LSP — принцип подстановки Барбары Лисков.** Принцип сознательно ограничен дополнительным условием для `ElectricScooter`. Базовый `Transport` считает объект подходящим новичку при `EaseOfUse >= 6`, но `ElectricScooter` переопределяет `IsNoviceFriendly` и дополнительно проверяет скорость. Например, `EaseOfUse = 8` и `MaxSpeedKmh = 30` дают `false`.

Это осознанный компромисс: ограничение скорости необходимо по правилам безопасности предметной области. Хотя оно сужает обещание базового класса, `FleetReportService` использует готовое свойство `IsNoviceFriendly` и не пересчитывает правило самостоятельно. Поэтому отчёты согласованно применяют единое решение модели, а исключение остаётся локальным.

| --- | ---: |

| Покрытие ветвей | 108 из 108 (100%) |

Основные группы тестов:

- `TransportTests`, `ElectricScooterTests`, `ElectricBicycleTests`, `ThingTests` — валидация, интерфейсы и правила для новичков.
- `ServiceCenterTests`, `FleetTests` — техосмотр, приёмка, отказы и уникальность номеров.
- `FleetReportServiceTests` — подсчёты, энергопотребление, фильтрация и сортировка.
- `InventoryNumberGeneratorTests` — префиксы и числовые суффиксы.
- `DependencyInjectionTests` — регистрация и подмена зависимостей.
- `ConsoleApplicationTests` — консольный сценарий.

**Ключевые тесты:**

- `FleetTests.Add_InspectionRejected_ReturnsReasonAndDoesNotAddItem` — проверяет отказ в приёмке и отсутствие отклонённого объекта в парке.
- `FleetTests.Add_WithRealServiceCenter_UsesInspectionLimit` — проверяет граничные значения техосмотра, включая 49 и 50.
- `ElectricScooterTests.IsNoviceFriendly_FastScooterWithHighEaseOfUse_StillNotForNovices` — проверяет дополнительное ограничение скорости для новичков.
- `DependencyInjectionTests.Fleet_ResolvedFromContainer_UsesSubstitutedServiceCenter` — проверяет, что `Fleet`, полученный через DI, использует подменённый сервис техосмотра.
- `ConsoleApplicationTests.Program_Main_ExercisesMenuAndDemonstration` — проверяет работу меню и демонстрационного сценария.

**Как устроена подмена зависимости.** В `TestFactory.RejectingServiceCenter()` создаётся `Substitute.For<IServiceCenter>()`, для которого метод `Inspect()` настроен возвращать причину отказа. В `DependencyInjectionTests` подмена регистрируется в `ServiceCollection`; контейнер передаёт её в конструктор `Fleet`. Это позволяет проверять реакцию парка на результат техосмотра без использования реального сервиса.

Тесты покрывают бизнес-правила, граничные значения и взаимодействие компонентов. Автоматизированная проверка консольного сценария дополняет тесты бизнес-логики, но не гарантирует проверку всех возможных последовательностей пользовательского ввода.

## Консольное меню

В `MainMenu` доступны следующие пункты:

| Пункт | Действие |
| --- | --- |
| `1` | `Accept transport` — добавить транспорт |
| `2` | `Accept a thing` — добавить вещь |
| `3` | `List of items` — показать имущество на балансе |
| `4` | `Number of items` — показать общее количество и количество по типам |
| `5` | `Total energy consumption` — показать суммарное суточное энергопотребление |
| `6` | `Suitable for novices` — вывести устройства для новичков |
| `7` | `Run the ready-made scenario` — запустить демонстрационный сценарий |
| `0` | `Exit` — завершить работу |

Демонстрационный сценарий показывает успешную приёмку и отказ по техосмотру, граничную оценку 50, ограничения для новичков, добавление вещей, ошибочные данные, повторные номера и формирование отчётов.

## Возможности расширения

- **Новый тип имущества.** Объект, реализующий `IInventoryItem`, можно добавить в `Fleet` без изменения механизма хранения. Отчёты общего количества и инвентарного списка смогут учитывать его автоматически. Для выбора объекта через консоль нужно обновить `MainMenu.AddThing()` и демонстрационный сценарий.
- **Новый транспорт.** Создаётся наследник `Transport` с необходимыми интерфейсами. Учёт и отчёты используют общие контракты, но выбор нового типа потребует изменения `MainMenu.AddTransport()` и демонстрационного сценария.
- **Сотрудники.** Не относятся к имуществу парка, поэтому для них нужны отдельные модель и хранилище.
- **Склад запчастей.** Следует реализовать как самостоятельную область с собственными правилами учёта.

Разделение бизнес-логики и `Demo` позволяет в будущем добавить другой интерфейс взаимодействия без переноса в него правил учёта.

## Запуск

Требуется .NET SDK 10.0. Команды выполняются из корня репозитория.

**Запуск приложения:**

```bash
dotnet restore VyshKat.sln
dotnet run --project VyshKat/VyshKat.csproj
```

**Запуск тестов:**

```bash
dotnet test VyshKat.sln
```

**Тесты с отчётом покрытия:**

```bash
dotnet test VyshKat.sln --collect:"XPlat Code Coverage"
```

Cobertura-отчёт создаётся в `Vyshkat.Tests/TestResults/<идентификатор запуска>/coverage.cobertura.xml`.
